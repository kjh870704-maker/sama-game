## 1. 기술 스택

| 계층 | 선택 | 근거 |
|---|---|---|
| **코어 로직** | **TypeScript (런타임 의존성 0)** | 렌더러·플랫폼 비의존. 헤드리스 실행이 가능해야 밸런스 시뮬(§6)이 성립 |
| **렌더링** | **PixiJS 8** (WebGL2/WebGPU) | 2D 스프라이트 배칭이 핵심 요구(PF-03). 드로우콜 제어가 직접 가능 |
| **UI 셸** | HTML/CSS 오버레이 | 전투 HUD·메뉴는 DOM이 압도적으로 빠르게 만들어짐 |
| **모바일 패키징** | Capacitor | 웹 빌드 1벌로 iOS/Android/PC 동시 대응 |
| **빌드** | Vite | — |
| **테스트** | Vitest | 코어가 순수 TS라 단위 테스트가 그대로 돈다 |
| **데이터 검증** | JSON Schema (draft-07) + 의미론 검증기 | §5 |

### 1.1 왜 Unity/Godot가 아닌가

기각한 이유는 "웹이 좋아서"가 아니라 **PRD R6(32스테이지 × 2난이도 = 64회 밸런스 QA)** 때문이다.

- 이 프로젝트의 최대 반복 비용은 렌더링이 아니라 **밸런싱**이다.
- 순수 TS 코어는 전투를 **초당 수천 회 헤드리스로 돌릴 수 있다.** 실제로 현재 `tools/sim.ts`는 8스테이지 × 2난이도 × 100회(= 1,600전투)를 20초 안에 끝낸다.
- 엔진에 로직이 묶이면 이 루프가 사라지고, 64회 QA는 전부 수동 플레이가 된다.

> **단, 코어는 렌더러를 전혀 모른다.** 만약 나중에 Godot/Unity로 갈아타더라도 교체 대상은 표현 계층뿐이며, `packages/core`는 그대로 이식된다. 이 경계가 스택 선택의 위험을 낮춘다.

## 3. 아키텍처의 핵심: 명령 + 결정론

전체 설계에서 가장 중요한 결정 하나.

> **모든 상태 변경은 `Command`를 통과하고, 모든 확률은 시드된 RNG 하나에서만 나온다.**

이 단일 결정이 PRD의 서로 달라 보이는 요구사항 3개를 한꺼번에 해결한다.

| 요구사항 | 이 구조에서 어떻게 해결되는가 |
|---|---|
| **S-09 무르기 (P0)** | 명령 실행 직전 `state.snapshot()`을 쌓고, 무르기는 `restore()`. **역연산을 작성하지 않는다** — 새 기믹이 추가되어도 무르기가 깨질 수 없다 |
| **리플레이/버그 재현** | `(시드, 명령 시퀀스)`만 저장하면 전투가 완전히 재현된다. 버그 리포트가 2줄이 된다 |
| **R6 밸런스 QA** | 플레이어를 AI로 대체하고 시드를 바꿔가며 N회 실행 → 클리어율 자동 집계 |

### 3.1 무르기가 RNG까지 되돌리는 이유

극한 난이도는 확률 특성(금격 `instantKill`, 책략 방어술 `strategyEvasion`)을 전제로 설계된다. 무르기가 RNG 상태를 복원하지 않으면 **"무르고 다시 하면 결과가 바뀌는"** 리롤 도박이 되어버려, 확률 특성 기반 설계가 무너진다.

현재 구현은 RNG의 내부 state까지 스냅샷에 포함하므로, 무르고 같은 명령을 다시 내면 **반드시 같은 결과**가 나온다. (테스트: `battle.test.ts › 무르기`)

> 이는 "확률을 되돌려 유리한 결과를 뽑는" 용도가 아니라 **"다른 수를 두기 위한"** 무르기라는 뜻이다. 조조전 원작의 무르기와는 의미가 다르므로, §8 미결 항목으로 올린다.

## 4. 특성 시스템 — 훅 파이프라인

원작 기준 특성은 100종을 훌쩍 넘는다. 전투 로직 안에 `if (hasTrait(...))`를 쌓으면 유지 불가능해진다. (PRD R7)

### 4.1 구조

```ts
defineTrait({
  id: "physicalDamageReduction",
  name: "물리 피해 감소",
  hooks: {
    onDefend(ctx, self, param) {
      if (ctx.kind === "physical") ctx.reduction = combine(ctx.reduction, param / 100);
    },
  },
});
```

피해 계산은 `DamageContext`를 만들고 → 공격자/방어자의 모든 특성 훅을 순서대로 통과시킨 뒤 → 최종 수치를 낸다. **`formulas.ts`는 특성 ID를 하나도 모른다.**

### 4.2 감소율은 곱연산으로 합성한다

```ts
combine(a, b) = 1 - (1 - a) * (1 - b)
```

덧셈으로 합치면 `물리피해감소 60% + 방어력보조 60% = 120%` → **무적**이 된다. 원작에서 특정 장수가 사실상 공략 불가가 되는 사고의 전형적 원인이다. 곱연산은 100%에 점근할 뿐 도달하지 않는다. (테스트: `formulas.test.ts › 피해 감소 특성은 곱연산으로 합성`)

### 4.3 훅 목록

| 훅 | 시점 |
|---|---|
| `onAttack(ctx, self, param)` | 보유자가 공격할 때 |
| `onDefend(ctx, self, param)` | 보유자가 피격당할 때 |
| `onTurnStart(self, param)` | 턴 시작 |
| `counterLimit(param)` | 반격 횟수 상한 덮어쓰기 |
| `ignoresRoughTerrain` | 이동 비용 무시 |

새 특성을 추가할 때 **전투 코드는 수정하지 않는다.** `defineTrait` 호출 하나면 된다.

## 5. 콘텐츠 = 데이터

### 5.1 원칙

> **새 스테이지를 추가할 때 `packages/core`의 파일은 한 줄도 바뀌지 않아야 한다.**

스테이지는 `packages/data/stages/*.json`이며, 기믹은 `trigger` → `action` 쌍으로 표현된다. 기믹 모듈(M-01~M-23)은 이 조합의 이름표일 뿐, 각각을 위한 특수 코드는 없다.

상세 매핑은 [`기믹-모듈-구현사양.md`](./기믹-모듈-구현사양.md) 참조.

### 5.2 맵 포맷 — ASCII

맵 에디터가 나오기 전까지 기획자가 텍스트로 직접 그릴 수 있어야 한다.

```json
{
  "legend": { ".": "plain", "^": "mountain", "F": "fort" },
  "rows":    ["^^^...FF...^^^", "..."],
  "heights": ["33300011000333", "..."],
  "regions": { "central_fort": { "x": 10, "y": 6, "w": 2, "h": 2 } }
}
```

`regions`는 승리 조건·이벤트 트리거·유닛 배치가 모두 참조하는 **이름 붙은 좌표 집합**이다. 좌표를 스테이지 JSON에 직접 박지 않으므로, 맵을 수정해도 스테이지 로직이 깨지지 않는다.

### 5.3 난이도는 파생시킨다

적 배치를 난이도별로 두 벌 관리하면 **한쪽만 고치는 실수가 반드시 난다.**

스테이지 데이터는 **일반 난이도 기준으로 한 번만** 작성하고, 극한은 `enemyLevelShift`로 파생시킨다.

```ts
enemyLevelShift = difficulty[extreme].minEnemyLevel - difficulty[normal].minEnemyLevel
```

> 이 규칙이 없었을 때 실제로 사고가 났다. 초기 S1-08 데이터는 이벤트 스폰에 `"level": 23`을 하드코딩했고, 시뮬레이터가 **극한 클리어율 100%**를 보고했다 — 극한에서도 적이 23레벨로 나왔기 때문이다. 수정 후 50.5%로 정상화되었다.

### 5.4 CI 검증 (`tools/validate-stages.ts`)

| 검사 | 근거 |
|---|---|
| 성능 예산 초과 | PRD §9.1 — Tier A/B/C 유닛 상한 |
| 인장 3개 · 슬롯1 = `clear` | PRD §5.2 |
| 편입 아군 + 손실 인장 → note 필수 | **PRD R-5.5** |
| 극한 적 레벨 ≥ 일반 | — |
| 인장 표현식 파싱 가능 | 오타난 인장이 "항상 달성"으로 조용히 동작하는 것 방지 |
| 참조 영역이 맵에 실재 | — |
| 참조 특성이 레지스트리에 실재 | — |

## 6. 밸런스 시뮬레이션 (`tools/sim.ts`)

PRD R6(64회 QA)와 §11(KPI)에 대한 자동화 대응.

```
$ npm run sim -- "" 100

스테이지 8개 × 100회 시뮬레이션

✅ S1-01 [normal ] 클리어 100.0% | 평균   4.1턴 | 인장2   2.0% | 인장3 100.0%
✅ S1-04 [normal ] 클리어   4.0% | 평균  28.0턴 | 인장2   4.0% | 인장3   0.0%
✅ S1-06 [extreme] 클리어  70.0% | 평균  10.2턴 | 인장2  68.0% | 인장3  70.0%
⚠️  S1-08 [extreme] 클리어 100.0% | 평균   7.0턴 | 인장2 100.0% | 인장3 100.0%   ← 목표(30.0%) 대비 과도하게 쉬움
```

### 6.1 무엇을 구동하는가 — 규칙 계층을 그대로 쓴다

시뮬레이터는 **플레이어가 실제로 쓰는 규칙 계층(`packages/web`의 `Session`)** 을 구동한다.
코어 + 스테이지 JSON만으로 돌리면 시나리오 단계·남문 통행료·민중 무장처럼
`Session.advanceScenario()`에만 있는 규칙이 빠져, **데이터상으로는 달성 불가능한
승리 조건**을 측정한다. 실제로 그 상태에서 8스테이지 중 5개가 클리어율 0%로
보고되었고, 원인은 난이도가 아니라 측정 대상이 틀린 것이었다.

> 대가: §3의 "core는 어떤 것도 import 하지 않는다"가 시뮬레이터에서는 성립하지
> 않는다. `Session`은 TS 파라미터 프로퍼티를 쓰므로 node의 strip-only 모드로
> 읽히지 않아 vite의 SSR 로더로 불러온다. 규칙이 코어+데이터로 되돌아오면
> 시뮬레이터도 코어만으로 돌릴 수 있게 되돌려야 한다.

부대 수준은 `recommendedLevel`이 아니라 **캠페인 누적 성장**으로 잡는다 — 일반은
캠페인 순서대로 여기까지 온 상태, 극한은 일반을 완주한 뒤 재도전하는 상태다.
`recommendedLevel`을 쓰면 후반 스테이지를 1장 수준 부대로 재게 된다.

### 6.2 자동 플레이가 쓰는 수단

`decide()`만으로는 측정되지 않는 수단을 러너가 보완한다. 이 셋이 없으면 각각
S1-04·S1-06이 클리어율 0%로 잡힌다.

| 수단 | 사용 조건 | 이유 |
|---|---|---|
| 일기토 · 설전 | 능력치 우위가 있고, 지금 달려야 하는 유닛이 아닐 때 | 레벨 차가 큰 보스를 평타로 넘길 수 없는 스테이지의 의도된 해법 |
| 구급약 | 체력 50% 미만, 달려야 하는 유닛이 아닐 때 | 보스전에서 먼저 쓰러지는 것을 막는다 |
| 점령 목표 제외 재판단 | 점령 명령이 규칙으로 거절될 때 | 거절된 명령만 되풀이하며 턴을 버리는 것을 막는다 |

> "달려야 하는 유닛"은 미충족 `reach` 조건이 지목한 유닛이다. 도주·잠입
> 스테이지(S1-02·S1-03)는 한 턴을 다른 데 쓰면 그대로 잡힌다. 단, 앞 단계로
> "특정 적 격퇴"가 남아 있으면 아직 달릴 때가 아니다(S1-04).

### 6.3 해석 규칙

AI 자동 플레이는 **사람 실력의 하한선 근사치**다. 목표 클리어율을 그대로 요구하지 않는다.

| 신호 | 의미 | 조치 |
|---|---|---|
| AI 클리어율 **0%** | 사람에게도 거의 확실히 과하다 | 🔴 릴리즈 차단 |
| AI 클리어율이 목표 +40%p 초과 | 설계 의도보다 쉽다 | 🟡 검토 |
| 타임아웃 발생 | 교착 상태 기믹 존재 | 🟡 검토 |
| 인장2·인장3 획득률이 **동일** | 속도 인장과 조건 인장이 상충하지 않음 | 🟡 **R-5.3 위반 의심** |

> 현재 S1-08은 인장2·3 획득률이 100%로 동일하다. 이는 R-5.3("인장 2와 3은 상충해야 한다")이 아직 성립하지 않는다는 뜻이며, 실제로 그렇다 — AI가 이기는 경로가 하나뿐이라 두 인장이 같이 붙는다. M2에서 조정 대상.

## 7. 성능 설계 (PRD §9 대응)

| 요구 | 구현 방침 | 상태 |
|---|---|---|
| **PF-01** 적 턴 일괄 처리 | `Battle.runAiPhase()` — 연출 없이 상태만 전진 | ✅ 구현됨 |
| **PF-05** AI 시간 분할 | `Battle.stepAi()` = **호출 1회당 유닛 1기**. 루프는 호출자(프레임 스케줄러)가 소유 | ✅ 구현됨 |
| **PF-02** 화면 밖 컬링 | 렌더 계층 | M1 후반 |
| **PF-03** 스프라이트 배칭 | PixiJS 단일 아틀라스, 드로우콜 예산 명시 | M1 후반 |
| **PF-04** 저사양 모드 | 이펙트 간소화 + 자동 쾌속 | M1 후반 |
| **PF-06** Tier C 실기 검증 | CI 머지 게이트 | M2 |

### 7.1 AI가 루프를 소유하지 않는 이유

```ts
// ✅ 호출자가 프레임 예산을 통제할 수 있다
while (frameBudgetRemaining()) battle.stepAi();

// ❌ 80유닛 AI가 한 프레임을 통째로 먹는다
battle.runAllAi();
```

`decide(state, unit)`는 **상태를 변경하지 않는 순수 함수**다. 덕분에 Web Worker로 옮기거나 결과를 캐싱하는 선택지가 나중에도 열려 있다.
